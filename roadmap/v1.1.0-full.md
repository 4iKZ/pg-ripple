## v1.1.0 - Prepared SPARQL Query Registry and Client Conveniences

**Theme:** Add the smallest useful stored-query lifecycle on top of the proven v1 binding, prefix, plan-cache, and streaming contracts.

> **Effort estimate:** 4-6 person-weeks

### Public API

```sql
pg_ripple.prepare_sparql(
    name text,
    query text,
    parameter_schema jsonb,
    prefix_mode text default 'strict',
    replace boolean default false
) returns jsonb

pg_ripple.execute_sparql(
    name text,
    bindings jsonb
) returns setof jsonb

pg_ripple.drop_prepared_sparql(name text) returns boolean
pg_ripple.list_prepared_sparql() returns table(...)
```

Only SELECT, ASK, CONSTRUCT, and DESCRIBE are supported. Query parsing, query-form checks, typed parameter-schema validation, and prefix-policy validation happen before catalog mutation. SPARQL Update fails explicitly.

### Catalog

Create `_pg_ripple.prepared_sparql` with an identity key, owner-scoped unique name, query text and form, typed parameter schema, strict/registered prefix mode, prefix generation when applicable, schema and extension generations, and creation/update timestamps.

Direct DML is revoked. Public functions validate all input and enforce ownership. The owner may prepare, replace, and drop; other roles require an explicit execute grant. Replacement preserves or resets grants according to one documented, regression-tested policy.

### Execution and Invalidation

- Convert supplied bindings with the v0.135 parser and RDF term validation.
- Reject missing, extra, or wrong-type values before execution.
- Use the same algebra, typed SQL parameter, plan-cache, decode, and observability paths as ad hoc SPARQL.
- Reuse v0.134 bounded-memory streaming, deadlines, disconnect cancellation, backpressure, and connection cleanup where results are delivered over HTTP.
- Pin strict or registered prefix policy at prepare time. Local query declarations retain precedence.
- Recompile when schema, applicable prefix, or extension generation changes. Never run a stale compiled plan.
- Do not add per-query HTTP routes, another execution engine, a scheduler, or stored credentials.

`list_prepared_sparql()` exposes stable metadata needed by clients: name, owner, query form, parameter schema, prefix mode, created/updated times, and whether recompilation is required. It never exposes another owner's query text without the documented privilege.

### Migration

Create `sql/pg_ripple--1.0.0--1.1.0.sql` with the catalog, constraints, indexes, ownership/grants, and public functions not supplied by generated extension SQL. The migration must preserve the v1 public surface and pass fresh-install versus upgrade schema and privilege comparison.

### Required Test Matrix

#### Validation Unit Tests

- Valid SELECT, ASK, CONSTRUCT, and DESCRIBE queries.
- SPARQL Update and malformed query rejection.
- Valid URI and literal parameter declarations.
- Missing, extra, duplicate, malformed, and unsupported parameter declarations.
- Strict and registered prefix policies, including unknown prefixes and local overrides.
- Catalog remains unchanged after every validation failure.

#### Lifecycle Regression Tests

- Prepare, list, execute, replace, and drop.
- Duplicate owner/name behavior with and without `replace`.
- Commit and rollback around prepare, replace, grant, and drop.
- Empty results and every supported query form.
- Existing one-shot SPARQL APIs remain unchanged.

#### Security and Privilege Tests

- Owner versus non-owner prepare, inspect, replace, execute, grant, revoke, and drop.
- Explicit execute grants and revocation take effect immediately.
- Direct catalog INSERT/UPDATE/DELETE is denied.
- Binding payloads containing SPARQL or SQL syntax remain data.
- Query metadata and error output do not disclose unauthorized query text or bindings.

#### Cache and Invalidation Tests

- One prepared query with 100 values reuses a compiled shape and remains value-correct.
- Parameter-schema or prefix-policy differences produce distinct plans.
- Committed schema, registered-prefix, and extension generation changes force recompilation.
- Rolled-back generation changes preserve the previous compiled plan and results.
- Concurrent execution during invalidation observes a transactionally valid old or new state, never a mixed state.

#### Streaming Regression Tests

- Large result memory remains bounded.
- Slow clients apply backpressure.
- Deadlines and disconnects cancel PostgreSQL work.
- Pool/session cleanup remains correct after success and cancellation.
- Typed JSON/CSV/TSV and N-Triples output matches equivalent ad hoc execution.

#### Fuzz and Migration Tests

- Fuzz query metadata and parameter schemas for panic, validation bypass, and malformed SQL.
- Apply `1.0.0 -> 1.1.0` to populated v1 installations with multiple owners and grants.
- Compare fresh and upgraded schema, constraints, privileges, functions, API metadata, and behavior.

### Blocking Jobs

```text
regress-v110-prepared-queries
prepared-query-schema-validation
prepared-query-permissions
prepared-query-invalidation
prepared-query-bindings-cache
prepared-query-streaming-regression
prepared-query-fuzz-smoke
migration-100-to-110
fresh-vs-upgrade-110
```

Every blocking job reports assertion counts and uploads raw evidence. Required jobs cannot skip successfully, use `continue-on-error`, or use `|| true`.

### Exit Criteria

- Read queries and typed schemas are validated before storage.
- Ownership and explicit execute grants are enforced without direct catalog access.
- Execution reuses v1 binding, cache, streaming, cancellation, and observability paths.
- Generation changes trigger correct transactional invalidation.
- Fresh and upgraded installations are equivalent.
- All blocking checks pass with retained evidence.
