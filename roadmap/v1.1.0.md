# v1.1.0 - Prepared SPARQL Query Registry and Client Conveniences

**Status:** Planned

**Effort estimate:** 4-6 person-weeks

**Goal:** Build on the stable v1 typed-binding and streaming contracts with a small, governed registry for reusable read queries. Prepared queries are validated before storage, retain typed parameter schemas and prefix policy, enforce ownership and execute grants, and reuse the existing query engine rather than creating another execution path.

## Deliverables

- [ ] Add `pg_ripple.prepare_sparql(name, query, parameter_schema, prefix_mode := 'strict', replace := false)`.
- [ ] Add `pg_ripple.execute_sparql(name, bindings)` and execute through the v0.135 typed-binding path and v0.134 streaming machinery.
- [ ] Add `pg_ripple.drop_prepared_sparql(name)` and `pg_ripple.list_prepared_sparql()`.
- [ ] Store owner, query form, typed parameter schema, prefix policy/generation, schema generation, and timestamps in `_pg_ripple.prepared_sparql`.
- [ ] Support read query forms only; parse and validate queries and parameter schemas at prepare time.
- [ ] Require owner or explicit execute privilege; preserve grants across replacement and upgrade according to the documented contract.
- [ ] Recompile on schema, prefix, or extension generation changes without exposing stale plans.
- [ ] Provide stable list/introspection output so SQL and client libraries can discover names, query forms, parameters, and ownership.

## Required Blocking Checks

| Check | Required evidence |
|---|---|
| `regress-v110-prepared-queries` | Prepare, execute, list, replace, drop, transaction rollback, and every supported read form return correct results. |
| `prepared-query-schema-validation` | Invalid queries, Updates, malformed parameter schemas, missing/extra/wrong-type bindings, and prefix-policy errors fail before catalog mutation. |
| `prepared-query-permissions` | Ownership, explicit execute grants, replacement, drop, cross-role access, and direct catalog DML boundaries are enforced. |
| `prepared-query-invalidation` | Schema, prefix, and extension generation changes trigger correct recompilation; rolled-back changes preserve prior behavior. |
| `prepared-query-bindings-cache` | Different values reuse one validated query shape without changing result correctness or treating values as syntax. |
| `prepared-query-streaming-regression` | Large execution reuses bounded-memory streaming, backpressure, timeout, cancellation, and clean pool/session behavior. |
| `prepared-query-fuzz-smoke` | Query metadata and parameter-schema fuzzing never panics, bypasses validation, or emits malformed SQL. |
| `migration-100-to-110` | Existing v1 installations gain the catalog, functions, ownership defaults, and grants through the required migration. |
| `fresh-vs-upgrade-110` | Fresh and upgraded schemas, privileges, APIs, and behavior are equivalent. |

Every blocking job reports assertion counts and uploads raw evidence. Required checks cannot skip successfully, use `continue-on-error`, or use `|| true`.

## Explicitly Deferred

- SPARQL Update and stored credentials.
- Automatic HTTP route generation, scheduling, or workflow semantics.
- Jupyter, LangChain/LlamaIndex, dbt, Kafka, Cypher/GQL, and other ecosystem packages; track them as separate packages or later roadmap versions.

## Exit Criteria

- Queries and typed parameter schemas are validated before storage.
- Owner and execute-grant boundaries pass positive and negative tests.
- Execution reuses v1 bindings, plan caching, streaming, cancellation, and observability.
- Schema, prefix, and extension changes invalidate plans correctly and transactionally.
- Migration and fresh-install equivalence gates pass.
- All named blocking checks pass with retained evidence.
